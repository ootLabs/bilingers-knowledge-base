# Multi-language readiness

> Status: **UI copy layer implemented (T-14), the rest not implemented.** `frontend/lib/i18n/` is a dependency-free dictionary lookup; Polish (`locales/pl.ts`) is the only registered locale. Knowledge base language tagging and language-aware retrieval, described below, are still design notes, not code.

## Why it is a first-class concern

An app about bilingualism that only ever works in one language is an awkward thing. Multi-language support is in the project scope from the start - as *architecture readiness*, not as content that exists today.

## The three layers, kept separate

| Layer | Today | Requirement |
|---|---|---|
| UI copy | Polish | Never hardcode strings in components once a second language is real; the backend returns data and keys, never sentences |
| Knowledge base content | Polish | Each unit carries a language tag from the start - retrofitting this is painful |
| Model answers | Polish | Answer in the user's language, but **only** from passages in a language the base actually has |

## The trap

The dangerous case is a user asking in language A when the knowledge base only holds language B. Translating on the fly quietly breaks grounding: the model is now paraphrasing across languages with no source to cite, and errors are invisible to a reviewer who reads only one of them.

Decide deliberately whether that is allowed, and if so, whether the answer is marked as translated. Do not let it happen by accident because retrieval ignored language.

## Rules that hold now, before any second language exists

- Knowledge base units carry a language field from day one.
- Retrieval filters by language rather than mixing.
- No Polish strings outside the frontend copy layer - not in the backend, not in error messages returned by the API.
- Repository language stays English regardless (see `AGENTS.md`), so adding a language never touches code identifiers.

## Open questions

- Which language comes second, and does the foundation intend to author it or translate it?
- Is the knowledge base translated as a whole, or per-topic as capacity allows?
- Language detection: from the browser, an explicit switch, or the language of the question?

## What T-14 built (the UI copy layer only)

- `frontend/lib/i18n/config.ts` defines `SUPPORTED_LOCALES` (today just `["pl"]`) and the `Locale` type derived from it.
- `frontend/lib/i18n/locales/pl.ts` is the Polish dictionary, a plain nested object.
- `frontend/lib/i18n/translations.ts` maps each `Locale` to its dictionary. Adding a second locale means creating `locales/<code>.ts` with the same shape as `pl.ts` and adding one line to that map; TypeScript fails the build if the new file's keys do not match `pl.ts`, so a partial translation cannot ship silently.
- `frontend/lib/i18n/index.ts` exports `getTranslations(locale?)`, returning a `t(key)` function that resolves a dot path (e.g. `"nav.chat"`) into a string. A missing key returns the key itself and logs a warning outside production, rather than throwing or rendering blank.
- No context provider and no client-side language switch exist yet, on purpose: nothing in scope activates a second language today, and building the switch now would be guessing at a UI nobody has asked for.

Design tokens (colors, font, button radius) live separately in `frontend/app/globals.css`, sourced from the T-03 branding research and explicitly marked provisional there pending T-03's open questions (see `docs/architecture.md`'s decisions table and the comment at the top of that file). They are not part of the i18n layer, but they came in with the same T-14 card.
