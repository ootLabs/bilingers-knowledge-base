# Project log

Short, dense record of what happened and why. Newest first.

**Read the top 3-5 entries** when picking up work - not the whole file. This is a log, not a manual: durable knowledge belongs in `docs/architecture.md` (decisions), `docs/map/` (where things live), or `docs/conventions.md` (how we write things). If a fact matters in three months, it goes there and gets a pointer here, not a permanent home in this file.

## Format - keep it strict

```
## YYYY-MM-DD - short title
**Done:** what now works, one line.
**Decisions:** what was chosen and why, one line each. Non-obvious only.
**Watch out:** what will bite next time. Omit the line if nothing will.
```

**Cap: 20 entries.** Adding the 21st? Move the oldest to `docs/log-archive/<year>.md` in the same commit. The cap is the point - an unbounded journal is a file nobody reads and every session pays for.

Each entry ≤ 5 lines. Do not narrate process, list files changed (git knows), or restate what the map already says.

## 2026-09-08 - panel second factor: TOTP and backup codes (T-83)
**Done:** `panel_totp_secrets` and `panel_backup_codes` (migration `c9a4d1f6b820`), enrolment/confirm/disable under `/api/panel/users/me/two-factor`, an administrator's reset for a lost phone, and a setup screen at `/panel/security` written for somebody who has never heard the word TOTP. `resolve_session`/`revoke_session`/`revoke_all_sessions` moved to `app/services/panel_sessions.py`.
**Decisions:** The code travels in the same request as the password, so every attempt at it is a full login attempt and inherits the per-IP throttle and the per-account lockout for free; a challenge endpoint would have needed both reimplemented. "Needs a second factor" is signalled in an `X-Second-Factor` header (listed in the CORS `expose_headers`), because the frontend still never reads a failed response's body.
**Watch out:** No QR code, the key is typed by hand, because a QR library is a dependency decision and not a drive-by install; if the editors find typing it painful, that is the card to open. `PANEL_TOTP_ENCRYPTION_KEY` has no value in `.env.example` on purpose, so 2FA is off until somebody generates one per environment. Rotating that key makes every existing secret unreadable and answers 503 on login for anyone enrolled; there is no re-encryption path yet.

## 2026-09-08 - panel editor and version history (T-87)
**Done:** `/panel/documents/new`, `/panel/documents/[id]` and `/panel/documents/[id]/history`. Saving posts a new version, the screen says which version and date it is editing and whether that version is the published one, and a save answers with a sentence naming the version it created. History previews an older version against the current one as a line diff and restores by copying forward.

## 2026-09-07 - document content and version model (T-84)
**Done:** `documents` and `document_versions` in `backend/app/models/document.py`, migration `ebedc16a4160` chained onto panel auth. 297 backend tests at 100% coverage, verified through a full upgrade/downgrade/upgrade cycle.
**Decisions:** Content lives on the version, not the document, so `documents` carries only `id`/`created_at` and every edit is a new row, never an `UPDATE`. "At most one published version per document" is a partial unique index (`document_versions_one_published_per_document`) rather than a `published_version_id` pointer, which would need a circular foreign key between the two tables. `author_id` is a foreign key to `panel_users` (`ON DELETE SET NULL`), not free text, matching the precedent already set by `panel_login_attempts.panel_user_id` now that panel accounts (T-82) exist.
**Watch out:** Immutability of a version is not database-enforced, nothing stops a raw `UPDATE document_versions`; it holds only because no service code performs one and no `updated_at` column exists to bump. `KnowledgeBaseVersion.document_versions` needs `passive_deletes="all"`, same trap as `KnowledgeBaseVersion.queries`, or the `RESTRICT` on `knowledge_base_version_id` never fires through the ORM. A partial index needs `sqlite_where` alongside `postgresql_where`: with only the PostgreSQL keyword the condition is dropped silently everywhere else, so on `panel_db` the index became an unconditional unique on `document_id` and refused a document its second version. That holds for every conditional index added from here on.

## 2026-09-03 - panel authentication, third review round (T-82)
**Done:** Three findings from the review of PR #7 closed: an address carrying a NUL byte (or any control character) is refused by `app.schemas.panel` with a 422 instead of passing `[^@\s]`, surviving `normalise_email`'s `strip()` and being refused by psycopg as an unauthenticated 500 with no audit row; every panel service function a router or the session dependency calls now carries `unavailable_on_database_failure`, so a dropped connection anywhere in the panel answers 503 rather than leaking `SQLAlchemyError` into a 500; and wrong passwords are no longer charged against a deactivated account's lockout counter.
**Decisions:** The 503 is translated by one `@app.exception_handler` in `main.py`, not by an `except` in each handler: `resolve_session` fails inside `current_panel_session`, so on every authenticated request there is no handler body to catch it. A decorator rather than chat's explicit `try`/`except` because the panel's rule is uniform - chat has to separate a `DataError` on bad input (422) from an outage, while the panel validates every string at the boundary, so there is no client-fault branch to keep. The lockout skips a deactivated account because that account cannot log in with any password, so the counter protects nothing, and `update_panel_user` does not clear `locked_until` on reactivation: five requests from anyone would leave the owner facing a 401 on their own correct password. The attempt is still recorded with its real reason (`bad_password`), so nothing disappears from the audit trail. Two findings from the same review did **not** survive verification: bcrypt 4.2.1 neither raises nor truncates on a NUL byte in a password (checked, and now pinned by tests in `test_security.py`), so the password path was never a 500; `_absent_password_hash` moved to `secrets.token_hex(32)` anyway, as hardening with no behaviour change, so the unknown-account path stops depending on that tolerance.
**Watch out:** `create_panel_user` re-raises an `IntegrityError` that is not the email uniqueness constraint, and its decorator now turns that into a 503 rather than a 500 - deliberate (the boundary validated the input, so it is the server that is wrong), but it means an unexpected future constraint on `panel_users` will read as an outage. A driver failure while recording a throttled attempt answers 503 instead of the 429 it was about to send.

## 2026-09-03 - panel authentication, second review round (T-82)
**Done:** Closed the rest of PR #7: the lockout counter's `FOR UPDATE` re-select now carries `populate_existing`, without which it handed back the identity-map object unchanged and counted from the value read before bcrypt, leaving the race the previous round claimed to close wide open; `PANEL_LOGIN_IP_MAX_ATTEMPTS` and `PANEL_LOGIN_IP_WINDOW_MINUTES` reach the container, so the throttle is configurable rather than pinned at 20 per 5 minutes; `change_password` clears `failed_login_count` and `locked_until`, matching `set_password_with_token`; a throttled login leaves one `ip_throttled` row per address per window instead of no trace at all; `migrated_database` skips on any missing mapped table, not just a missing `alembic_version`, so a database on another branch's head skips with a hint instead of failing six integration tests on `relation "panel_users" does not exist`.
**Decisions:** The throttle records the first refusal in each window and stays silent for the rest (`TooManyAttempts.first_in_window`): the audit table has to show that a flood happened without becoming the thing the flood fills, and retention is still open (B-07). `_client_ip`'s docstring now states the proxy assumption as a condition of deployment, since the throttle keys on that value and a load balancer in front would put the whole foundation in one bucket. The counter race is tested by moving the column with `synchronize_session=False` and leaving the mapped object stale, not with threads: that is the identity-map staleness itself, deterministic, and it fails without the fix.
**Watch out:** The per-IP throttle is still in-process, so it is per replica and resets on restart. `test_panel_auth.py` is now three files (login, lockout, throttle) and `attempts_for` moved into `conftest.py`, so a test importing it from `tests.test_panel_auth` will not find it.

## 2026-09-02 - panel authentication review fixes (T-82)
**Done:** Addressed PR #7 review: unique Alembic revision id (no longer colliding with `feat/cost-ledger`'s `0002`); a locked, deactivated or nonexistent account all answer login with the same `401` and timing; `_register_failure` closes the lockout counter race under `SELECT ... FOR UPDATE`; a per-IP throttle (`app.services.rate_limit`, swept every 1000 calls so it cannot grow forever) turns away a flood before it pays for bcrypt; a correct password on a deactivated account no longer counts against the lockout; `create-admin` validates its email argument; a reset token can no longer be issued for a deactivated account; `change_password` invalidates any live reset token, and a superseded token is marked `used_at` instead of having its `expires_at` quietly rolled back; `IntegrityError` on account creation only becomes `EmailAlreadyUsed` when it names the email uniqueness constraint (by name on PostgreSQL, by substring as a SQLite fallback); the two ~580/360-line test files are now seven files under 300 lines each, split along existing class boundaries.
**Decisions:** Every login refusal (unknown address, wrong password, locked, deactivated) is one `AuthenticationFailed` with the same generic detail; `verify_password` runs once, unconditionally, right after the account lookup, so timing cannot distinguish the branches either. Whether an account is locked is still visible in `panel_login_attempts.reason`, just not over HTTP. The row lock for the counter race is taken only inside `_register_failure`, around the write, not around the bcrypt comparison that precedes it - locking earlier would serialise concurrent *legitimate* logins on the same account for the length of a bcrypt hash. The per-IP limiter is in-process (a dict behind a lock, not Redis): the stack has one backend process today, and this exists to blunt casual hammering, not to survive multiple replicas. CLI diagnostics stay in English, matching the rest of `app.cli` - only product-facing copy is Polish.
**Watch out:** The rate limiter's state is process-global and does not reset itself between tests; `panel_client`/`postgres_panel_client` in `conftest.py` call `rate_limit.reset()` for that reason. It also will not work correctly if the backend is ever run as more than one process - revisit with a shared store first. No automated test proves the lockout counter race fix under real concurrency (two threads, two connections); the fix follows a standard `FOR UPDATE` pattern but is only verified by the full suite passing, not by a dedicated concurrency test.

## 2026-08-31 - cost ledger, configurable price list, reporting views (T-41)
**Done:** `queries` now stores cost in USD **and** PLN with `fx_rate_pln_per_usd` and `pricing_version` on the row (a new Alembic revision), guarded by three check constraints. `app.services.pricing` loads a JSON price list from `PRICING_FILE` and re-reads it when the file changes; `app.services.usage` prices a `TokenUsage` and completes the ledger row. Views `query_costs` and `query_costs_monthly` sum per day, model, account and month, and `scripts/cost_report.py` prints all four plus a `--csv` export. 137 backend tests at 100% coverage; live price reload, the downgrade/upgrade cycle, and an upgrade over a pre-0002 partial-cost row all verified in the container.
**Decisions:** Both currencies are stored because they answer different questions (the provider invoices in USD, the foundation approves PLN under D11) and because converting at report time would silently restate history once the rate moves. Prices live in a file, not env vars or a table: a table needs an admin surface that does not exist, and env vars need a container recreate, which is the deploy the card rules out. A broken or missing price list fails the request loudly rather than falling back to the previously loaded one, because quietly pricing traffic with superseded numbers corrupts the ledger for as long as nobody looks. The measurement is written by a single conditional `UPDATE` matching only an unmeasured row, not a read followed by a write, because the latter lets two concurrent writers both pass the guard and one replace a cost that was already reported; every failure path rolls back, so a rejected attempt leaves the row writable instead of looking like an overwrite. A measurement the database refuses raises `InvalidUsage`, not `UsageNotRecorded`, since the latter invites a retry that would fail identically. The cost ledger revision clears pre-existing `cost_usd` values that have no PLN amount beside them and then adds the provenance constraint validated, rather than adding it `NOT VALID`: such a figure has no rate and no price list version, so it was never reportable, while an unvalidated constraint would leave `pg_dump` permanently disagreeing with `app.models.chat`. Unmeasured means `cost_pln IS NULL` alone, the definition `query_costs_monthly` counts by; also matching `model IS NULL` would refuse a row that named its model before pricing succeeded and report it as already measured. `record_usage` owns the session it commits, with `session_factory` only for test doubles: usage is known after the stream ends, when the request session is closed, so there is no caller transaction to join and none to roll back on someone else's behalf. Two model names that differ only in surrounding whitespace are refused: the parser strips, so JSON's two distinct keys would otherwise collapse into one and the second entry would silently reprice every question at another tier's rate. Prices and the exchange rate also have an upper bound, because a value like `1e30` passes every other check and then raises a bare `decimal.InvalidOperation` out of the quantize step. The price list cache is keyed by the bytes last parsed rather than by `stat()`, since a bind mount or network filesystem may report mtime to the whole second and a same-second edit of identical length would otherwise be invisible; the bytes are compared directly rather than hashed, because they are already in hand and equality beats a probabilistic claim of it. `query_costs` joins `chat_sessions` with `LEFT JOIN`, which is row-identical given a NOT NULL foreign key to a primary key and lets the planner drop the join entirely for any rollup that does not group by account. Granularity stayed one row per query rather than a `model_calls` child table: nothing yet makes two model calls per question, and T-40 can add one when its router actually exists. Reporting is views plus a script, not an endpoint, since there is no auth and an endpoint exposing spend would be public. The views deliberately carry no personal data, so a monthly figure can go to the foundation without a stripping step. `committed_token` moved into `conftest.py` and gained `committed_query` and `priced_usage`, rather than a second copy in the new test modules.
**Watch out:** Nothing writes a measurement yet, on purpose: no model is called, so every row still has NULL tokens and NULL cost, and the reports honestly total zero. The feedback loop into T-02.2 therefore starts with T-30/T-40, not now. `cost_usd` alone is no longer a valid row: `queries_cost_requires_pricing_provenance` wants all four cost columns or none, which is why `test_models.py`'s round trip had to supply them. Report buckets are `Europe/Warsaw`, not UTC, so a day boundary in the views will not match a naive `date_trunc` on `created_at`. `cost_report.py` filters `created_at` over a half-open range instead of comparing the view's computed `report_month`, which is what lets the existing `ix_queries_created_at` serve it; the bounds must be `TIMESTAMP` literals, because `DATE 'x' AT TIME ZONE zone` picks the timestamptz overload and lands four hours past the boundary the views bucket on. Real prices go in `backend/pricing.json`, which is gitignored and absent on a fresh clone. `alembic check` catches column and index drift but **not** check constraints or views, so those are guarded by tests instead: `test_models.py` compares the ORM's constraint names against `pg_constraint` and asserts none is left unvalidated, and `test_cost_reporting.py` pins the view inventory. Neither `alembic check` nor the pre-commit hook runs in CI, so both are advisory. `scripts/` still has no test harness at all (`check_map.py`, `check_text.py`, `smoke_test.py` are equally uncovered), so `cost_report.py` is verified by hand; the fragile part is gone rather than tested, with PostgreSQL formatting the month via `to_char` instead of this script slicing psql output whose date format follows the server's DateStyle.

## 2026-08-26 - streaming chat endpoint skeleton (T-12)
**Done:** `POST /chat` accepts `{question, session_token}`, upserts a `ChatSession` by token, writes and commits a `Query` row, then streams a fixed sequence of opaque placeholder chunks (`text/plain`). No retrieval, model call, or orchestration yet. `backend/app/services/`, `backend/app/schemas/` created with their first files. 73 backend tests at 100% coverage.
**Decisions:** `get_or_create_chat_session` only flushes a new row inside a SAVEPOINT (`session.begin_nested()`); `record_query`'s commit makes both it and the query durable together, so a failure between the two never leaves an orphaned session, and a lost insert race is recovered by re-reading the row (and bumping `last_active_at` on it) without discarding any other pending work in the same transaction. `answer` stays NULL throughout: no model runs, and the `queries_answer_requires_kb_version` constraint would reject a non-null answer with no knowledge base version anyway. Service failures raise `ChatServiceUnavailable` (503, infra) or `InvalidChatInput` (422, only for a `DataError` such as a NUL byte); an `IntegrityError` on `record_query`'s commit is deliberately treated as infra (503), since the only constraint it can realistically violate is the `chat_session_id` foreign key, meaning the session vanished mid-request rather than the client sending something wrong. Placeholder chunks are opaque keys, not prose: `docs/llm/i18n.md` bans hardcoded Polish in the backend, and `docs/conventions.md` bans sentences in general, in any language. `session_token` requires 32-64 lowercase hex characters, closing a collision/quota-bypass gap a one-character token would have left open on data marked `PERSONAL_DATA`. Moved `db_session`/`migrated_database` test fixtures from `test_models.py` into `conftest.py`, now matching `SessionLocal`'s `autoflush=False, expire_on_commit=False` so the fixture's semantics match production traffic.
**Watch out:** `ChatRequest` relies on `ConfigDict(str_strip_whitespace=True)` so stripping happens before `max_length` is checked; a hand-rolled `field_validator` would run after Field-level constraints and reject valid, merely padded input. The `Depends(get_session)` session closes as soon as the sync handler returns the `StreamingResponse`, before any bytes are actually sent - harmless while `stream_placeholder_answer` never touches the database, but whatever adds real per-chunk work later (T-40/T-41) needs its own session opened inside the generator, not this one.
